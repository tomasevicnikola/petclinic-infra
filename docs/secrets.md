# Secrets

Every secret in the dev project, who made it and who can read it.

| Secret | What it is | Created by | Stored in | Who can read | Rotation | Notes |
| --- | --- | --- | --- | --- | --- | --- |
| `dev-db-app-password` | Password of the `petclinic` MySQL user | `modules/cloudsql`, `random_password.app` | Secret Manager, user-managed replica in `europe-west3` | `sa-app-vm@petclinic-capstone.iam.gserviceaccount.com` — `roles/secretmanager.secretAccessor` on this secret (`google_secret_manager_secret_iam_member.app_password_accessor`) | Bump `db_password_version` in `envs/dev` and apply; the MySQL user and the new secret version change together | Value is in Terraform state |
| `dev-db-app-config` | Host, port, database and user as JSON | `modules/cloudsql`, from instance attributes | Secret Manager, user-managed replica in `europe-west3` | `sa-app-vm@petclinic-capstone.iam.gserviceaccount.com` — `roles/secretmanager.secretAccessor` on this secret (`google_secret_manager_secret_iam_member.app_config_accessor`) | Follows the instance; no manual step | Holds no password on purpose, so the application reads two secrets |
| `dev-grafana-admin-password` | Grafana admin login | `modules/secrets`, `ephemeral.random_password.grafana_admin` | Secret Manager, user-managed replica in `europe-west3` | Nobody yet. The binding is added with the monitoring stack that consumes it | Bump `grafana_password_version` in `envs/dev` and apply; Grafana's own copy has to be updated in the same change | Value never enters state |
| `dev-ansible-vault-password` | Password for `ansible-vault` encrypted files | `modules/secrets`, `ephemeral.random_password.ansible_vault` | Secret Manager, user-managed replica in `europe-west3` | `sa-ops-vm@petclinic-capstone.iam.gserviceaccount.com` — `roles/secretmanager.secretAccessor` on this secret (`google_secret_manager_secret_iam_member.ansible_vault_accessor`) | `ansible-vault rekey` every encrypted file first, then bump `vault_password_version` and apply | Value never enters state. Read by `scripts/fetch-vault-pass.sh` |

Bindings are per secret. No consumer holds a project-level Secret Manager role,
so a service account that can read one secret cannot list or read another.

Two identities can read everything, both from bootstrap and both intentional:
project Owner, and `sa-terraform`, which holds `roles/secretmanager.admin`
because it creates the secrets. `sa-cicd` holds nothing at all yet.

## Two tiers

Secret Manager is the primary store. Everything the infrastructure, the
database and CI need lives there, generated by Terraform, encrypted with
Google-managed keys, read at runtime through per-secret IAM.

Ansible Vault is the second tier and covers only Ansible's own values —
variables inside a playbook that have to travel in git. Its password is not one
of those: it comes from Secret Manager through `scripts/fetch-vault-pass.sh`,
which prints it on stdout for `vault_password_file` and writes nothing. So the
vault password never sits on disk, and nothing encrypted with it is readable
from the repo alone.

## Secrets in state

Terraform generates passwords, and by default a generated password is written
to state in cleartext. The state bucket is the mitigation: versioned,
CMEK-encrypted with `tf-state/tfstate-key`, public access prevented, readable
only by `sa-terraform`.

The two secrets in `modules/secrets` go further and never reach state at all.
They use `ephemeral` `random_password` with the write-only `secret_data_wo`
argument: the value is generated in memory during the run and handed to the
provider on apply, and Terraform stores nothing but the counter
`secret_data_wo_version`, which is what decides when a new secret version is
written. Terraform 1.11, google 6.14 and random 3.7 are the floors for this,
and the repo is above all three.

The database password in `modules/cloudsql` is still on the classic path and is
a known follow-up: moving it needs a matching change to `google_sql_user`,
whose password is also a write-only argument, and that is a separate apply from
this one.
