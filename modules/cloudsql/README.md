# cloudsql

MySQL 8 on a private IP, the `petclinic` database, and the user the application
connects as. The password is generated and written to Secret Manager; host,
port, database and user go to a second secret as JSON.

Exposes the instance and connection names, the private IP, the database and user
names, and the two secret ids. Never the password.

The private IP comes out of the PSA range the network module reserved, so this
attaches to that peering instead of creating one. Backups and binary logs are on
for point-in-time recovery, `local_infile` is off, deletion protection is on in
dev too, and `sa-app-vm` can read these two secrets and nothing else. TLS is
required but unverified — no CA reaches the client, which is the trade for a
database only reachable from inside the VPC, so clients still ask for it with
`sslMode=REQUIRED`.

Both passwords are generated by `ephemeral` `random_password` and written
through write-only arguments, so neither reaches state or a plan file. The
application password goes to Secret Manager; root's goes nowhere at all, which
locks the account behind a value nobody holds — reset it with
`gcloud sql users set-password` if it is ever needed.

Rotate by bumping `password_version` (`db_password_version` in `envs/dev`) and
applying. The user, root and the secret version all read that one number: the
user and the secret must share it, because they take their value from the same
ephemeral password in the same run, and root joins them because rotating it
costs nothing. The MySQL user is updated before the new secret version is
published, and existing connections survive the change.

If an apply dies part way through a rotation, bump `password_version` again
rather than re-running it. A version already recorded in state is not resent, so
a half-finished rotation can leave the database on one password and the secret on
another, and only a fresh number moves both. Old secret versions are disabled
rather than destroyed, so a rotation can be rolled back — but disabled is not
deleted, and rotating away from a leaked password means destroying the old
version by hand.
